# Astronaut Health Monitoring API
## Frontend Integration Documentation — v0.4.0

**API Version:** `0.4.0`  
**Shuffler Version:** `2.1.0`  
**Base URL:** `http://127.0.0.1:8080`  
**API Prefix:** `/api/v1`

---

## 1. Overview

The Astronaut Health Monitoring API provides synthetic astronaut telemetry, evaluates incoming measurements, and exposes health findings, environmental information, and crew alerts.

This project is an **educational monitoring simulator**, not a diagnostic medical system. Its findings are generated from configured evaluation rules and synthetic measurements. They must not be interpreted as medical diagnoses or used as a substitute for professional medical assessment.

### Main responsibilities

| Component | Responsibility |
|---|---|
| `shuffler.py` | Generates synthetic astronaut, environmental, ISS, space-weather, and radiation data. |
| `condition_engine.py` | Validates measurements and evaluates health findings. |
| `main.py` | Coordinates data refreshes, evaluations, API responses, alarm verification, daily entries, and crew acknowledgements. |
| Frontend | Displays API data and sends user actions. It does not independently evaluate health conditions. |

### Important architecture rules

- Three astronauts are supported: `user1`, `user2`, and `user3`.
- Each astronaut has independent physiological data, simulation scenarios, profiles, and ECG generation.
- Environmental and external data sources are shared across astronauts.
- Each astronaut snapshot is evaluated independently.
- The condition engine is stateless: it evaluates the supplied snapshot rather than maintaining a historical condition state.
- API data and daily entries are currently stored in memory. They are not persistent across backend restarts.
- The frontend must use the backend's status and quality fields rather than deriving its own health classifications.

## 2. General API conventions

### 2.1 HTTP methods

| Method | Purpose |
|---|---|
| `GET` | Retrieve current data. |
| `POST` | Submit a scenario, daily entry, or crew acknowledgement. |

### 2.2 Content type

Requests with JSON bodies must use:

```http
Content-Type: application/json
```

### 2.3 Astronaut identifiers

Supported identifiers:

```text
user1
user2
user3
```

An unsupported astronaut identifier results in an error response.

### 2.4 Data refresh

The backend refreshes its data approximately every **2 seconds**.

Recommended frontend polling interval:

```text
2–5 seconds
```

The frontend should avoid unnecessarily frequent requests.

A successful HTTP response does not necessarily mean that every measurement is valid. Always inspect the corresponding `quality` field.

## 3. API Endpoints

### 3.1 Health

#### `GET /health`

Checks whether the backend is available.

Example:

```http
GET /health
```

Use this endpoint to verify backend connectivity before starting frontend polling.

---

### 3.2 Crew overview

#### `GET /api/v1/crew`

Returns the crew overview, including astronaut information and crew-level alert information.

The response includes:

- Crew members.
- Current astronaut status information.
- Latest daily-entry information, where available.
- Unresolved crew alert count.
- Crew alerts.

This endpoint is intended for the team overview screen.

---

### 3.3 Crew alerts

#### `GET /api/v1/crew/alerts`

Returns the current crew alerts.

Alerts are generated by the backend after a life-threatening candidate has passed the verification period.

The frontend should distinguish between:

- A health finding that is currently a candidate.
- A confirmed crew alert.
- An alert that has been acknowledged.
- An alert that has been resolved.

The existence of a `life_threatening_candidate` finding does not, by itself, mean that a confirmed crew alert already exists.

#### `POST /api/v1/crew/alerts/{alert_id}/acknowledge`

Acknowledges a crew alert.

**Request body:**

```json
{
  "response": "I_AM_OK"
}
```

or:

```json
{
  "response": "INTERVENING"
}
```

Supported acknowledgement values:

| Value | Meaning | Result |
|---|---|---|
| `I_AM_OK` | The astronaut reports that they are okay. | Resolves the alert. |
| `INTERVENING` | An intervention is in progress. | Marks the alert as being handled; does not automatically resolve it. |

The frontend must send one of the supported values exactly as written.

Example:

```http
POST /api/v1/crew/alerts/1/acknowledge
Content-Type: application/json
```

```json
{
  "response": "INTERVENING"
}
```

The alert identifier must refer to an existing alert.

## 4. Astronaut-specific endpoints

The following endpoints use the astronaut identifier in the URL.

### 4.1 Dashboard

#### `GET /api/v1/astronauts/{astronaut_id}/dashboard`

Returns the astronaut's current monitoring dashboard data.

Example:

```http
GET /api/v1/astronauts/user1/dashboard
```

The dashboard response provides the frontend with:

- API version and generation timestamp.
- Current simulation scenario.
- Overall status.
- Active health findings.
- Telemetry measurements.
- Measurement quality information.

The dashboard is intended to be the primary data source for an astronaut monitoring screen.

### 4.2 Health conditions

#### `GET /api/v1/astronauts/{astronaut_id}/conditions`

Returns the condition evaluation results for the specified astronaut.

Example:

```http
GET /api/v1/astronauts/user1/conditions
```

The response includes:

- Overall status.
- Evaluated findings.
- Measurement quality information.

A finding represents an evaluation result based on the available measurements. It is not a medical diagnosis.

### 4.3 Telemetry

#### `GET /api/v1/astronauts/{astronaut_id}/telemetry`

Returns the astronaut's telemetry data.

Example:

```http
GET /api/v1/astronauts/user1/telemetry
```

Telemetry measurements use a common structure:

```json
{
  "value": 75,
  "unit": "bpm",
  "measured_at": "2026-11-15T10:30:00+00:00",
  "quality": "VALID"
}
```

The example illustrates the measurement structure. Actual values and timestamps are generated by the backend.

Available physiological measurements include:

| Measurement | Unit |
|---|---|
| Heart rate | bpm |
| Blood pressure | mmHg |
| Heart rate variability | ms |
| Respiratory rate | breaths/min |
| Oxygen saturation | % |
| Body temperature | °C |
| Blood glucose | mg/dL |
| Stress | Backend-defined measurement unit |
| Sleep | Backend-defined measurement unit |
| Activity | Backend-defined measurement representation |

Telemetry may also include environmental and system-related information. Use the dedicated environment and space-data endpoints for shared environmental and external data.

### 4.4 Simulation scenario

#### `GET /api/v1/astronauts/{astronaut_id}/scenario`

Returns the currently configured simulation scenario for the astronaut.

#### `POST /api/v1/astronauts/{astronaut_id}/scenario`

Changes the simulation scenario for the specified astronaut.

**Request body:**

```json
{
  "mode": "ABNORMAL",
  "abnormalities": [
    "HYPERGLYCEMIA"
  ]
}
```

Supported modes:

| Mode | Description |
|---|---|
| `NORMAL` | Normal synthetic measurements. |
| `REST` | Resting state. |
| `EXERCISE` | Exercise state. |
| `SLEEP` | Sleeping state. |
| `ABNORMAL` | Applies the specified abnormality scenario or scenarios. |

Supported abnormalities:

| Abnormality | Description |
|---|---|
| `HYPERGLYCEMIA` | Elevated synthetic blood glucose. |
| `HYPOGLYCEMIA` | Low synthetic blood glucose. |
| `TACHYCARDIA` | Elevated heart rate. |
| `BRADYCARDIA` | Low heart rate. |
| `HYPOTHERMIA` | Low body temperature. |
| `FEVER` | Elevated body temperature. |
| `HYPOXEMIA` | Reduced oxygen saturation. |
| `TACHYPNEA` | Elevated respiratory rate. |
| `HYPERTENSION` | Elevated blood pressure. |
| `HYPOTENSION` | Low blood pressure. |
| `CARDIAC_ARREST` | Explicit synthetic cardiac-arrest scenario with heart rate set to zero. |
| `SEVERE_HYPOXEMIA` | Explicit severe oxygen-saturation scenario. |

Example — assign severe hypoxemia to `user2`:

```http
POST /api/v1/astronauts/user2/scenario
Content-Type: application/json
```

```json
{
  "mode": "ABNORMAL",
  "abnormalities": [
    "SEVERE_HYPOXEMIA"
  ]
}
```

Example — assign cardiac arrest to `user1`:

```json
{
  "mode": "ABNORMAL",
  "abnormalities": [
    "CARDIAC_ARREST"
  ]
}
```

**Important scenario rules:**

- Scenarios are independent per astronaut.
- Changing one astronaut's scenario must not change another astronaut's physiological scenario.
- Abnormality names are case-sensitive API values and must match the supported names.
- Conflicting abnormalities are rejected by scenario validation.
- `CARDIAC_ARREST` is an explicit synthetic scenario. Missing, stale, or invalid heart-rate data must never be interpreted as cardiac arrest.
- `CARDIAC_ARREST` produces a synthetic heart rate of `0 bpm` and a flatline ECG visualization.
- `SEVERE_HYPOXEMIA` produces a synthetic SpO₂ value of `65%` and respiratory rate of `28 breaths/min`.
- These values are simulation outputs, not real-world medical measurements.

### 4.5 ECG

#### `GET /api/v1/astronauts/{astronaut_id}/ecg`

Returns synthetic ECG samples for the specified astronaut.

Example:

```http
GET /api/v1/astronauts/user1/ecg?sample_count=25
```

Parameters:

| Parameter | Type | Default | Limits |
|---|---|---:|---|
| `sample_count` | Integer | 25 | 1–5000 |

Response structure:

```json
{
  "sample_rate_hz": 500,
  "unit": "mV",
  "sample_count": 25,
  "samples": [],
  "data_type": "SYNTHETIC_VISUALIZATION_ONLY"
}
```

The `samples` array contains the generated ECG values.

ECG properties:

- Sampling frequency: `500 Hz`.
- Unit: `mV`.
- Data type: `SYNTHETIC_VISUALIZATION_ONLY`.
- Samples are generated independently for each astronaut.
- During the explicit `CARDIAC_ARREST` scenario, the returned samples are zero-valued to display a synthetic flatline.

**ECG data is intended for visualization only. It must not be used for clinical interpretation.**

## 5. Daily entries

Daily entries allow an astronaut to submit basic self-reported information.

### 5.1 Submit a daily entry

#### `POST /api/v1/daily-entry`

**Request body:**

```json
{
  "astronaut_id": "user1",
  "sleep_hours": 7.5,
  "fatigue_level": 4,
  "stress_level": 6
}
```

Field validation:

| Field | Type | Allowed range |
|---|---|---|
| `astronaut_id` | String | `user1`, `user2`, `user3` |
| `sleep_hours` | Number | 0–24 |
| `fatigue_level` | Integer | 0–10 |
| `stress_level` | Integer | 0–10 |

The backend validates the submitted values.

The latest daily entry is stored separately for each astronaut.

**Storage limitations:**

- Daily entries are stored in memory.
- Only the latest entry per astronaut is retained.
- No historical daily-entry records are maintained.
- Entries are lost when the backend restarts.

### 5.2 Retrieve a daily entry

#### `GET /api/v1/astronauts/{astronaut_id}/daily-entry`

Example:

```http
GET /api/v1/astronauts/user1/daily-entry
```

Returns the latest daily entry for the requested astronaut, if one exists.

If no entry has been submitted, the frontend must handle the empty state rather than treating it as a normal daily entry.

## 6. Shared environment and space data

Environmental and external data are shared across astronauts and updated once per refresh cycle.

### 6.1 Environment

#### `GET /api/v1/environment`

Returns shared environmental information.

The environment data includes cabin-related measurements such as:

- CO₂ concentration.
- O₂ concentration.
- Cabin pressure.
- Humidity.
- Environmental temperature.

These measurements belong to the shared environment and should not be treated as independent astronaut physiological measurements.

The frontend can use this endpoint for the **Cabin Environment** monitoring section.

### 6.2 Space data

#### `GET /api/v1/space-data`

Returns shared space-related information, including available:

- ISS position and related information.
- Space-weather data.
- Radiation and dosimetry information.
- External-source metadata.

External data availability depends on the corresponding source and its update status.

Historical radiation archive data must not be presented as live radiation telemetry.

The frontend should inspect available metadata and timestamps before displaying external data as current.

## 7. Status and severity model

The backend uses four overall status values.

| API value | Frontend label | Meaning |
|---|---|---|
| `NORMAL` | Basit | No evaluated condition currently requires a higher status. |
| `CAUTION` | Riskli | Caution-level status or data-quality limitations. |
| `WARNING` | Tehlikeli | A warning-level condition has been evaluated. |
| `CRITICAL` | Aşırı tehlikeli | A critical-level condition has been evaluated. |

The frontend must display the status returned by the backend. It must not calculate its own overall status from raw measurements.

### 7.1 Important distinction: CRITICAL vs. life-threatening

`CRITICAL` and `life_threatening` are separate concepts.

- `CRITICAL` represents the severity of an evaluated finding.
- `life_threatening_candidate` identifies a finding that may qualify for the life-threatening alert verification process.
- A confirmed crew alert is created only after backend verification.

Therefore:

```text
CRITICAL does not automatically mean a confirmed crew alert.
```

The frontend must not create a crew alert merely because it receives a `CRITICAL` status.

## 8. Measurement quality

Every evaluated measurement has a quality classification.

| Quality | Meaning |
|---|---|
| `VALID` | Measurement is present, valid, and sufficiently recent. |
| `STALE` | Measurement exists but is older than its allowed freshness period. |
| `INVALID` | Measurement is invalid, non-finite, or otherwise fails validation. |
| `MISSING` | Measurement is not available. |
| `UNKNOWN` | Measurement quality cannot be established. |

### 8.1 Frontend handling

The frontend must not treat unavailable measurements as normal measurements.

Recommended handling:

| Quality | Suggested frontend behavior |
|---|---|
| `VALID` | Display the measurement normally. |
| `STALE` | Display the last value with a stale-data indication. |
| `INVALID` | Mark the measurement as invalid. |
| `MISSING` | Display an unavailable state. |
| `UNKNOWN` | Display an unknown-quality state. |

A missing heart-rate measurement is not evidence of cardiac arrest.

A stale or invalid measurement must not be used to confirm a life-threatening condition.

### 8.2 Measurement timestamps

Measurements may contain a `measured_at` timestamp.

The frontend should use this timestamp to communicate data freshness and avoid presenting old measurements as live values.

## 9. Condition evaluation and findings

The condition engine evaluates the available measurements independently for each astronaut.

Current supported conditions:

| Finding ID | Evaluation rule |
|---|---|
| `HYPERGLYCEMIA` | Blood glucose ≥ 145 mg/dL |
| `HYPOGLYCEMIA` | Blood glucose ≤ 69 mg/dL |
| `TACHYCARDIA` | Heart rate ≥ 105 bpm |
| `BRADYCARDIA` | Heart rate > 0 and ≤ 55 bpm |
| `HYPOTHERMIA` | Body temperature ≤ 34.8 °C |
| `FEVER` | Body temperature ≥ 37.8 °C |
| `HYPOXEMIA` | SpO₂ ≤ 94%, with respiratory rate used as supporting information where available |
| `TACHYPNEA` | Respiratory rate ≥ 22 breaths/min |
| `HYPERTENSION` | Systolic pressure ≥ 130 mmHg or diastolic pressure ≥ 80 mmHg |
| `HYPOTENSION` | Systolic pressure ≤ 99 mmHg or diastolic pressure ≤ 64 mmHg |
| `CARDIAC_ARREST` | Valid heart-rate measurement equal to 0 bpm |
| Severe hypoxemia | SpO₂ below 70% |

Thresholds are part of the simulator's evaluation configuration. They are not universal clinical diagnostic criteria.

### 9.1 Finding structure

A finding contains information such as:

```json
{
  "id": "TACHYCARDIA",
  "status": "WARNING",
  "title": "Elevated Heart Rate",
  "description": "The evaluated heart rate is above the configured threshold.",
  "observed_value": 120,
  "unit": "bpm",
  "measured_at": "2026-11-15T10:30:00+00:00",
  "quality": "VALID",
  "interpretation_ready": true,
  "recommendations": [],
  "related_measurements": [],
  "life_threatening_candidate": false
}
```

This is an illustrative example of a finding. Actual titles, descriptions, values, and related measurements depend on the evaluated condition.

### 9.2 Life-threatening candidates

The current engine can mark qualifying findings with:

```json
{
  "life_threatening_candidate": true
}
```

The field indicates that the finding is eligible for the backend's verification process.

Current explicit simulation cases include:

- Cardiac arrest.
- Severe hypoxemia.

A candidate is not the same as a confirmed crew alert.

## 10. Life-threatening alert verification

The backend applies a verification period before creating a confirmed crew alert.

### 10.1 Verification rules

The candidate must remain present with valid and sufficiently fresh measurements for at least **3 seconds**.

The backend uses monotonic elapsed time for this verification.

Verification is interrupted or reset when:

- The candidate condition disappears.
- Required measurements become missing.
- Required measurements become stale.
- Required measurements become invalid.
- The candidate is no longer supported by the evaluated snapshot.

The frontend does not run this timer and must not attempt to reproduce the verification logic.

### 10.2 Candidate vs. confirmed alert

| State | Meaning |
|---|---|
| Candidate | The condition is eligible for verification. |
| Confirmed alert | The backend has verified the candidate for the required duration. |
| Acknowledged | A crew member has responded to the alert. |
| Resolved | The alert has been marked as resolved. |

The frontend should use the crew alert endpoints to display confirmed alerts and their acknowledgement state.

## 12. Error handling

The API uses HTTP status codes to communicate request outcomes.

| HTTP status | Meaning |
|---|---|
| `200` | Request completed successfully. |
| `400` | Invalid request or unsupported scenario configuration. |
| `404` | Requested resource or astronaut was not found. |
| `422` | Request validation failed. |
| `503` | Service or required operation is temporarily unavailable. |

The frontend should handle unsuccessful responses explicitly.

Recommended behavior:

- Do not assume a failed request returned usable telemetry.
- Do not replace an error response with fabricated normal values.
- Preserve the last successfully retrieved data only if it is clearly marked as potentially outdated.
- Show an appropriate error or unavailable state.
- Retry temporary failures without creating an excessive request loop.

## 13. Recommended frontend integration workflow

### Initial loading

1. Request `GET /health`.
2. Request `GET /api/v1/crew`.
3. Request `GET /api/v1/environment`.
4. Request `GET /api/v1/space-data`.
5. Request the selected astronaut's dashboard.
6. Retrieve ECG samples if the ECG visualization is visible.

### Periodic refresh

Every 2–5 seconds:

1. Refresh the selected astronaut's dashboard or telemetry.
2. Refresh crew alerts.
3. Update environmental and external information according to the frontend's display requirements.
4. Preserve quality and timestamp information.
5. Update the interface using backend-provided status values.

### Daily entry workflow

1. Collect sleep, fatigue, and stress values.
2. Validate the input on the frontend for usability.
3. Submit the entry to `POST /api/v1/daily-entry`.
4. Refresh the astronaut's daily entry using the corresponding GET endpoint.

The backend remains responsible for final input validation.

### Crew alert workflow

1. Retrieve alerts from `GET /api/v1/crew/alerts`.
2. Display confirmed alerts and their current acknowledgement state.
3. Allow the user to submit `I_AM_OK` or `INTERVENING`.
4. Send the acknowledgement to the corresponding alert endpoint.
5. Refresh the alert list to display the backend's updated state.

## 14. Current limitations

The following limitations should be considered during frontend development:

- The system generates synthetic physiological measurements.
- The condition engine is rule-based and is not a medical diagnostic engine.
- Daily entries are stored in memory only.
- Crew alerts are stored in memory only.
- No persistent historical measurement database is currently provided.
- No user authentication or authorization is currently defined by this API contract.
- CORS is currently configured permissively and should be restricted before production deployment.
- External NASA and other data sources may be unavailable, delayed, rate-limited, or subject to source-specific update intervals.
- Some planned monitoring categories do not yet have actual measurement sources. Unsupported measurements must not be presented as real sensor readings.
- ECG is synthetic visualization data only.
- The 3-second alert verification is a simulator behavior and should be reconsidered before integrating real emergency-monitoring hardware.

---

## 15. Frontend implementation principles

1. Use backend-provided status values. Do not independently calculate overall health severity.
2. Use measurement quality values when displaying telemetry.
3. Distinguish a life-threatening candidate from a confirmed crew alert.
4. Do not infer cardiac arrest from missing or invalid heart-rate data.
5. Treat daily entries as self-reported information, not sensor measurements.
6. Keep astronaut-specific data separated by astronaut identifier.
7. Treat shared environmental and space data as shared information.
8. Do not present synthetic measurements as real sensor readings.
9. Do not present historical external data as live telemetry.
10. Handle unavailable data and API errors explicitly.
